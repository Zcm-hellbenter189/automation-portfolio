## 1. 测试对象与测试计划

### 1.1 业务流（4 个接口串联）

```
事务「1.登录」 POST /api/login          → JSON 提取器提取 data.token → 变量 token
事务「2.注册」 POST /api/register       → JSON 提取器提取 data.id    → 变量 uid
事务「3.查询」 GET  /api/users/${uid}
事务「4.下单」 POST /api/orders  {"user_id": ${uid}, ...}
```

### 1.2 关键配置

| 项 | 值 | 说明 |
|---|---|---|
| 线程数 | `${__P(threads,20)}` | 可用 `-Jthreads=N` 从命令行覆盖，便于梯度加压 |
| Ramp-Up | 5s | 逐步拉起，模拟真实用户涌入（设 0 = 冲击测试） |
| 循环次数 | 20 | 总样本 = 线程数 × 20 × 4 |
| 注册数据 | `压测用户_${__UUID()}` | **必须唯一化**（见 3.3） |
| 断言 | 响应断言（200）+ JSON 断言（`$.code == 0`） | 两层：HTTP 层 + 业务层 |
| 执行方式 | `jmeter -n -t plan.jmx -l r.jtl -e -o report` | **GUI 只用于编写调试** |

### 1.3 一个必答的坑：JMeter 提取出的变量是**字符串**

下单请求体写成 `{"user_id":"${uid}", ...}` → 实际发出 `"user_id":"403"`（**字符串**），
而服务端 `self.users` 的键是 **int** → `"403" not in {403: ...}` 为真 → 返回 `1005 用户不存在`。

**正解**：**数字字段不加引号**（`{"user_id":${uid}}`），字符串字段才加（`"${product}"`）。

> 顺带暴露一个设计问题：服务端把"类型不匹配"和"资源不存在"报成了同一个错误码，**排查时会走偏**。应分开报错。

## 2. 第一轮：连接层瓶颈（58 个 `Connection refused`）

### 2.1 现象

100 并发（8000 样本）时出现 **1.30% 错误率**：

| 错误类型 | 数量 |
|---|---|
| `HttpHostConnectException: Connection refused` | **58** |
| `401 Unauthorized` | 28 |
| `400 Bad Request` | 18 |

**但 TPS 大幅上涨（579→1654）、响应时间没有恶化（P95 仅 3ms）。**

### 2.2 推断：**不是处理能力问题**

> **"错误率上升 + 延迟没恶化 + 吞吐还在涨" → 请求根本没进去，问题在连接层。**

### 2.3 定位：Python 标准库的两个默认值

| 默认值 | 问题 | 修复 |
|---|---|---|
| `socketserver.TCPServer.request_queue_size = 5` | TCP accept 队列只有 **5**，瞬时连接超出即被 RST（Windows 下客户端看到 `Connection refused`） | 子类化 → `request_queue_size = 128` |
| `BaseHTTPRequestHandler.protocol_version = "HTTP/1.0"` | **每个请求都新建 TCP 连接**，把只有 5 个位置的队列反复冲击 | `protocol_version = "HTTP/1.1"`（**前提：响应必须带 `Content-Length`**，本项目已有 ✅） |

#### 为什么改成 HTTP/1.1 就不"每个请求新建连接"了？

**准确说法：HTTP/1.1 只是「默认允许」复用；真要复用，需要三层配合，缺一不可。**

| 层 | 负责什么 | 本项目状态 |
|---|---|---|
| **协议层** | HTTP/1.0 **默认非持久**（响应后即关连接）；HTTP/1.1 **默认持久**（keep-alive） | 需显式设 `protocol_version = "HTTP/1.1"` |
| **服务端** | 响应必须带 `Content-Length`（或 chunked）才能**分帧** —— 客户端靠它判断"响应体到哪结束、下一个响应从哪开始" | ✅ 已有 |
| **客户端** | **必须用连接池（`requests.Session`）才会复用**；裸 `requests.post()` 每次都新建临时 Session —— **即使协议是 1.1，照样每次新连接** | `HttpClient` 用 Session ✅ |

⚠️ **最容易误解的一点**：把服务端改成 HTTP/1.1，**不等于**客户端就会复用。**协议是"许可"，连接池才是"执行者"。**

**效果量化**（本项目 200 线程 × 循环 20）：

| 配置 | 建连次数 | 对 accept 队列的冲击 |
|---|---|---|
| HTTP/1.0 | 200 × 20 = **4000 次** | 反复冲击只有 5 个位置的队列 → 58 个 RST |
| HTTP/1.1 + Session | **≈ 200 次**（每线程复用 1 条连接跑完 20 个循环） | 降一个数量级；配合 `request_queue_size = 128` → 归零 |

**但注意：HTTP/1.1 的连接"不能真并发"。** 一条连接同一时刻只能处理一个请求（响应完了才能发下一个），这叫**队头阻塞（HOL blocking）**。所以 **200 个并发线程仍然需要约 200 条连接**（每线程一条）—— keep-alive 省掉的是"**同一线程循环多次**的重复建连"，不是"并发线程之间的连接"。

> 真正让"一条连接承载多个**并发**请求"的是 **HTTP/2 的多路复用（multiplexing）**，靠 stream id 区分。HTTP/1.1 的 keep-alive 只能**串行复用**。

**验证方法**：服务端每接受一个新连接，`setup()` 会被调用一次 —— 加条日志计数：

```python
def setup(self):
    super().setup()
    get_logger("mock").info(f"新连接来自 {self.client_address}")
```

客户端跑两种写法对比，看日志打了几次：

```python
# ① 裸调用：打 5 次（每次新建连接）
for _ in range(5):
    requests.get(url)

# ② Session：只打 1 次（复用同一条连接）
s = requests.Session()
for _ in range(5):
    s.get(url)
```

### 2.4 验证

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `Connection refused` | **58** | **0** ✅ |
| `401` | **28** | **0** ✅（自动消失，见第 3 节） |
| Avg | 1.27ms | **0.38ms** |
| P95 | 3.00ms | **1.00ms** |

**响应时间降到原来的 1/3** —— 这就是 keep-alive（连接复用）的收益。

## 3. 第二轮：因果链分析（1 个根因 + 2 类级联）

### 3.1 现象

修复连接层后，只剩 **87 个 `400/Bad Request`**，分布极其规律：

| 请求 | 错误数 |
|---|---|
| 登录 | **0** |
| 注册 | 29 |
| 查询 | 29 |
| 下单 | 29 |

**29 × 3 —— 均匀得不像巧合。**

### 3.2 因果链推断

```
根因：注册失败（29 次，实为 1006 撞名）
  ↓ uid 提取不到（JSON 提取器失败）
  ├─ 查询：GET /api/users/    ← 路径末尾为空 → int("") → 400/1002
  └─ 下单：{"user_id":, ...}  ← 非法 JSON → 服务端解析失败 → user_id 为 None → 400/1002
```

**登录为什么 0 错？** 因为**登录不依赖任何提取出的变量**（body 写死）。**这个对比本身就在提示"问题出在变量上"。**

### 3.3 根因修复：压测数据必须唯一化

注册名原为毫秒时间戳 → **并发下多线程落在同一毫秒 → 撞名（1006）**。
改为 `${__UUID()}` 后，**87 个错误全部归零**。

> **同一个"数据唯一化"的坑，本项目已踩过三次**：
> ① 功能测试固定名 `王五`（第二次运行必撞）；② xdist 并行下的 `依赖用户`；③ **压测并发注册**。
> **规律：只要是"并发/重复执行 + 唯一约束"，唯一性的来源就必须足够强。毫秒时间戳在单线程够用，一到并发就不够。**

### 3.4 核心方法论

> **看错误不能看有几类，要看有几条因果链。**
> 一个根因会生出很多种表象 —— 修掉根因，衍生现象会一起消失。
> **验证方式**：修掉你认为的根因，观察衍生现象是否同时消失（本次实证：修连接层 → 401 自己没了）。

## 4. 第三轮：数据量导致的系统性退化（单变量对照实验）

### 4.1 实验设计

| 项 | 设置 |
|---|---|
| 并发 | 200 线程 × 20 循环 × 4 请求 = 16000 样本/次 |
| **关键** | **连跑 5 次，期间不重启 mock_server** |
| 环境 | 关掉 PyCharm，内存占用 **8.6 / 15.7GB** |
| **唯一变化的自变量** | **users 表数据量（每轮 +4000 条）** |

### 4.2 结果：完美单调退化

| 次数 | TPS | Avg | Median | P90 | P95 | P99 | Max | Err |
|---|---|---|---|---|---|---|---|---|
| 1 | **3360.64** | 1.88ms | 1.00 | 5.00 | 7.00 | 13.99 | 77 | 0 |
| 2 | 3163.93 | 10.28ms | 8.00 | 20.00 | 25.00 | 39.00 | 102 | 0 |
| 3 | 2546.96 | 25.44ms | 18.00 | 51.00 | 67.00 | 104.00 | 266 | 1 |
| 4 | 2072.00 | 44.09ms | 31.00 | 90.00 | 119.00 | 190.99 | 534 | 1 |
| 5 | **1707.76** | **65.52ms** | 46.00 | 136.00 | 176.95 | 286.98 | 572 | 2 |
| **6（重启后）** | **3346.58** | **1.85ms** | 1.00 | 5.00 | 7.00 | 14.00 | 77 | 0 |

**TPS 降 49%、Avg 涨 35 倍，且单调；重启清空表后立刻恢复到起点（TPS 差 0.4%）。**

> **⇒ 清空数据 → 性能恢复 ⇒ 数据量是唯一根因，因果关系确证。**

### 4.3 退化的机制：两条 O(n) 路径

| 路径 | 代码 | 说明 |
|---|---|---|
| **注册判重** | `any(u["name"] == name for u in self.users.values())` | 每次遍历全表，表越大越慢 |
| **列表查询** | `list(self.users.values())` + `json.dumps` | 每次序列化整张表；200 并发一起做 → CPU 打满 |

**证据**：**5 次里注册始终是最慢的接口**（表空时也如此：2.11ms vs 下单 1.68ms）→ 判重开销**恒存在**，随表增长被放大。

### 4.4 ⭐ 最有价值的一课：**噪声会让你"看反"，而不是"看不准"**

**同一组实验，在被污染的环境下做过一次，结论完全相反**：

| | 上一组（内存仅剩 3.8GB） | 本组（内存 8.6GB） |
|---|---|---|
| 设置 | 同样 200 线程、同样不重启 | 同样 200 线程、同样不重启 |
| TPS 序列 | 2396 → 1908 → **2297**（**无单调性**） | 3361 → 3164 → 2547 → 2072 → 1708（**完美单调**） |
| 当时的结论 | "数据量影响被噪声掩盖" → **误判为"数据量不是主因"** | ✅ 数据量是唯一根因 |

> **上一组并非"数据量没影响"，而是"内存压力这个噪声把趋势盖住了"。**
> **⇒ 性能测试里"排除环境噪声"不是优化项，而是前提。**

### 4.5 顺带定位掉的两个"测量污染源"

| 污染源 | 机制 | 表现 |
|---|---|---|
| **压测机 GC 停顿** | JMeter 是 Java 程序，默认堆仅 1GB；Full GC 会 **Stop-The-World**，而这期间的停顿**会被算进 JMeter 记录的响应时间** | 偶发长尾（`Max` 达 2909ms，而 `Median` 仅 12ms） |
| **机器内存压力** | 可用内存不足 → 动用页面文件 → 磁盘换页比内存慢几个数量级 | 同上，且**掩盖了数据量趋势** |

> **对比：为什么被测的 Python 服务没有 GC 停顿问题？**
> CPython 以**引用计数**为主（增量回收，无需 STW），分代 GC 只用于处理循环引用，扫描范围小；而 JVM 的**追踪式 GC 必须冻结所有线程**才能准确扫描。**两者机制不同 → 长尾来源不同。**

## 5. 可复用的方法论（6 条）

1. **看错误不看"几类"，看"几条因果链"** —— 一个根因会生出多种表象。
2. **"错误率上升 + 延迟没恶化 + 吞吐还在涨" ⇒ 问题在连接/资源层，不是处理能力。**
3. **"Median 正常但 Max 大得离谱" ⇒ 某个环节发生了停顿**（GC / 换页 / 网络重传），而不是"负载高"。
4. **同一配置跑多轮、记录实验条件**（线程数、循环数、是否重启、内存占用）—— 波动 > 30% 时先解决可复现性，**再谈性能**。
5. **不只看平均值，看 P95/P99** —— 平均值会被长尾污染（实测：Median 12ms vs Avg 109ms，差 9 倍）。
6. **明确压测对象与测量边界** —— 压测机与被测服务不分离时，测出来的是"这台电脑"的极限。

## 6. 已知局限与改进方向（面试如实说）

| 局限 | 说明 | 改进方向 |
|---|---|---|
| **压测机与被测服务同机** | 400 个线程抢 16 核，JMeter 的 GC/内存压力会污染被测指标 | 分离部署；或用 Locust 分布式（master/worker）多机产生负载 |
| **被测对象是本地 Mock** | 单进程 + 一把全局锁 + O(n) 判重，**数字没有业务容量意义** | 换一个多进程（Gunicorn）+ 数据库的服务做对照 |
| **唯一性靠遍历实现** | `any(...)` 是 O(n) 内存扫描，且重启即失 | 数据库唯一索引 / 哈希索引 |
| **列表查询无分页** | 每次序列化整张表，随数据量线性恶化 | 加分页（`?page=&size=`）+ 只返回必要字段 |
| **未做拐点精定位** | 100~200 之间未逐档细分；且拐点可能受压测机限制 | 梯度加密 + 记录压测机 CPU |

### 6.1 展开：唯一性的三层实现（从「遍历」到「索引」）

**先分清两件事** —— `any()` 遍历同时藏着两个**互相独立**的问题，别混为一谈：

| 问题 | 性质 | 解决办法 |
|---|---|---|
| **O(n) 全表扫描** | **性能**问题 | 换索引结构（哈希 / 树）→ O(1) / O(log n) |
| **"检查 + 插入"非原子** | **并发**问题（TOCTOU） | 加锁（本项目已做），或**下沉给数据层** |

> ⚠️ **换成哈希索引只解决第一件，竞态照样在** —— **优化复杂度和解决并发是两码事。**

#### 层次一：内存哈希索引（成本最低，本项目可做）

```python
class MockHandler(BaseHTTPRequestHandler):
    users = {}
    _name_index = set()          # 新增：name 的唯一性索引
```

```python
with self._lock:                  # ← 仍然必须加锁："检查 + 插入"仍是复合操作
    if name in self._name_index:  # O(1)，不再遍历全表
        duplicate = True
    else:
        duplicate = False
        uid = MockHandler.next_user_id
        MockHandler.next_user_id += 1
        user = {"id": uid, "name": name, "age": body.get("age", 0)}
        self.users[uid] = user
        self._name_index.add(name)    # 与 users 同步维护
        snapshot = dict(user)
```

- **收益**：判重 O(n) → **O(1)**，表越大收益越明显
- **代价**：多一份状态，**两处必须同步维护**（漏一处就出现"表里有、索引里没有"的不一致）
- **未解决**：重启即失（Mock 的定位，见文末取舍）

#### 层次二：数据库唯一索引（生产正解）

```sql
CREATE TABLE users (
    id   INTEGER PRIMARY KEY AUTOINCREMENT,
    name VARCHAR(50) NOT NULL,
    age  INTEGER NOT NULL DEFAULT 0,
    CONSTRAINT uk_users_name UNIQUE (name)      -- 唯一性交给存储引擎
);
```

**关键转变：不再「先查后插」，而是「直接插、捕获冲突」。**

```python
try:
    cur.execute("INSERT INTO users(name, age) VALUES (?, ?)", (name, age))
    conn.commit()
except sqlite3.IntegrityError as e:      # 唯一约束被违反
    if "UNIQUE constraint failed" in str(e):
        self._send(400, {"code": 1006, "msg": "用户名已存在"})
        return
```

**为什么这才是对的（面试最值钱的一点）**：

> 应用层的 `SELECT ... 然后 INSERT` **本身就是 TOCTOU** —— 两个并发事务可能同时查到"不存在"。
> 而**数据库唯一索引在存储引擎层做原子检查**，天然免疫竞态。
> **⇒ 不变量应该由数据层强制，而不是靠应用层「自觉」。**

这也把本项目"把判重放进锁内"的正确做法提升到了**正确的抽象层级**：**锁是单进程内的权宜，唯一索引是跨进程/跨机的保证。**

| 方案 | 查重复杂度 | 重启存活 | 并发安全 | 多进程 / 多机 |
|---|---|---|---|---|
| `any()` 全表遍历 | **O(n)** | ❌ | 靠应用层锁 | ❌ |
| 内存 `set` 索引 | **O(1)** | ❌ | **仍靠应用层锁** | ❌ |
| **DB 唯一索引** | O(log n)（B+ 树） | ✅ | ✅ **引擎层原子** | ✅ |
| Redis `SETNX` | O(1) | 看持久化配置 | ✅ 单命令原子 | ✅ |

**各数据库的冲突异常**：SQLite → `sqlite3.IntegrityError`；MySQL → errno **1062**；PostgreSQL → SQLSTATE **23505**。

**⚠️ 唯一索引的前提仍然是「规范化」** —— 索引比的是**存进去的值**，字面不同就是两个值。所以应用层的 `strip()` 不能省；更彻底的做法是**在数据库层再收一道**：

```sql
-- PostgreSQL：函数索引，把「规范化」也交给数据层
CREATE UNIQUE INDEX uk_users_name ON users (lower(trim(name)));
```

> **⇒ 唯一性 = 规范化 + 强制约束，两件事都要做。**

#### 层次三：多机部署（Redis 前置，DB 兜底）

```python
if redis.set(f"user:name:{name}", uid, nx=True, ex=3600):   # SETNX，原子
    ...   # 抢到名额 → 继续写 DB
else:
    ...   # 已存在 → 1006
```

⚠️ **Redis 只能当前置拦截（降低 DB 压力），不能当唯一性的最终保证** —— 它会**过期**、主从切换可能**丢数据**、且与 DB **无法强一致**。

> 分布式基本纪律：**缓存能优化性能，不能保证一致性。** 最终唯一性必须由 DB 唯一索引兜底。

#### 关于「哈希索引」这个词

它是**数据库内部的索引结构**，不是让应用自己实现的：

| 索引类型 | 适用 | 复杂度 |
|---|---|---|
| **B+ 树**（默认） | 范围查询、排序、前缀匹配 | `=` 查询 O(log n) |
| **哈希索引** | **只支持 `=` 等值查询**，不支持范围 | O(1) |

唯一索引**通常建 B+ 树**就够了（除了查重，往往还要按 name 排序 / 范围查）。MySQL InnoDB 的**自适应哈希索引（AHI）是自动的**，不需要手工创建。
所以「改成哈希索引」更准确的表达是：**把唯一性判定从应用层遍历，下沉到数据层的索引结构。**

#### 本项目的取舍

| 选项 | 成本 | 建议 |
|---|---|---|
| 内存 `set` 索引 | 极低（改 3 行） | ✅ **推荐先做** —— 直接消掉实测的 O(n) 退化 |
| **SQLite**（`sqlite3` 是**标准库，零依赖**） | 中 | 想要"重启存活 + 真唯一索引"时做；注意 `check_same_thread` 与测试数据清理 |
| MySQL / PostgreSQL | 高 | 教学项目不必；**面试口述即可** |

**「重启即失」怎么写**：**它不是缺陷，是 Mock 的定位** —— 就该"不落盘、每次重启干净"。**在文档里写明这个边界，比假装它是数据库强。**

面试时把话说全：

> "Mock 里用内存索引是为了让压测靶子保持简单；**如果这是生产系统，唯一性必须由数据库唯一索引保证 —— 插入靠捕获 `IntegrityError`，而不是应用层先查后插。**"

## 7. 面试话术（3 分钟版）

> **【开场 20s】**
> "我用 JMeter 对着自己的 Mock 服务做了一次性能测试。业务流是登录拿 token → 注册 → 查询 → 下单，用 JSON 提取器做关联、两层断言。做完之后最大的收获不是数字，而是**三轮修复 + 两次发现测量工具本身在骗人**。"
>
> **【第一轮 · 连接层 40s】**
> "压到 100 并发时出现 1.3% 错误率。但有意思的是 —— **TPS 还在涨、响应时间反而更低**。这个组合说明请求根本没进去，问题在连接层。查下来是 `http.server` 的两个默认值：`request_queue_size` 默认只有 **5**（accept 队列太小，超出就被 RST），`protocol_version` 默认 **HTTP/1.0**（每个请求都新建连接，把队列反复冲击）。改成 128 和 HTTP/1.1 后，连接错误归零，**响应时间还降到了原来的 1/3**。"
>
> **【第二轮 · 因果链 40s】**
> "剩下的错误更有意思：87 个 400，其中注册、查询、下单各 29 个，**登录是 0**。我判断它们只有一个根因 —— 注册撞名失败导致 id 没提取到，查询的路径末尾变空、下单的请求体变成 `{"user_id":}` **非法 JSON**，于是都报了参数错误。**改成 UUID 唯一化后，87 个错误一起归零。** 这件事让我记住：**看错误不能看有几类，要看有几条因果链。**"
>
> **【第三轮 · 数据量 40s】**
> "最后一轮是连跑 5 次不重启服务。TPS 从 3360 **单调**降到 1708、延迟从 1.9ms 涨到 65ms，**唯一变化的变量是服务端累积的数据量**。原因是注册的唯一性检查是全表遍历、列表查询要序列化整张表，都是 O(n)。重启清空后性能立刻恢复，因果闭环。"
>
> **【收尾 · 反思 20s】**
> "但最值得说的是：**同一个实验我前面做过一次，结论完全相反** —— 因为当时机器内存只剩 3.8G，噪声把趋势盖住了，我一度认为数据量不是主因。关掉 PyCharm 后规律立刻显现。**所以我的结论是：性能测试里排除环境噪声不是优化项，而是前提 —— 否则噪声不会让你看不准，而是会让你看反。**"
