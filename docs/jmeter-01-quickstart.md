## 0. 先建立坐标系：JMeter 与你的框架的位置关系

**这不是"从零学一个新东西"，而是同一套测试模型换一种表达方式。**

| 你框架里的东西 | JMeter 里的元件 | 说明 |
|---|---|---|
| `conftest.py` 的 `auto_login` fixture | **事务控制器 + 仅一次控制器** | 前置动作：先登录拿 token |
| `core/extractor.py` + `VariablePool` | **JSON 提取器 / 正则提取器** | 从响应里取值 → 存成变量 → 后续请求引用（即"**关联**"） |
| `data/cases.yaml` 数据驱动 | **CSV Data Set Config** | 从文件读数据，一行一迭代 |
| `core/assertions.py` | **响应断言 / JSON 断言 / 持续时间断言** | 断言库 |
| `HttpClient` 的 headers 合并 | **HTTP 信息头管理器** | 统一注入请求头 |
| `config/config.yaml` 的 `base_url` | **HTTP 请求默认值** | 抽公共的协议/地址/端口 |
| 一条测试用例（多接口串联） | **事务控制器** | 把多个请求合并成一个"事务"，统计业务级 TPS |
| `created_user`（每用例独立数据） | **`__UUID()` / `${__threadNum}_${__time(,)}`** | 数据唯一化（**压测里同样是刚需**） |
| `pytest -n auto`（分进程） | **分布式压测（master/slave）** | 多机产负载 |
| `reports/report.html` | **聚合报告 / `-e -o` 生成 HTML 报告** | 结果呈现 |

> **面试可以直接说**：
> "JMeter 的元件和我在 pytest 框架里实现的东西是一一对应的 —— 提取器对应我的变量池，CSV Data Set Config 对应我的 YAML 数据驱动，断言对应我的断言库。**所以我理解的是这些元件背后的测试模型，而不是只会拖控件。**"

## 1. 安装

### 1.1 先装 Java（JMeter 是 Java 程序）

**检查是否已有**：

```bat
java -version
```

- 有输出（版本 ≥ 8）→ 跳到 1.2
- 提示"不是内部或外部命令"→ 需要装

**推荐**：Eclipse Temurin **JDK 17**（免费开源，JMeter 5.6.x 官方推荐版本）
下载后一路默认安装即可。**装完要新开一个终端**再验证（环境变量是登录时构建的 —— 这条你上次踩过）。

> 注：PyCharm 自带的 JBR 虽然也是 Java，但它不是系统级安装、不在 PATH 里，**不要试图拿它凑**，装个标准的更省事。

### 1.2 装 JMeter

1. 到 Apache JMeter 官网下载 **Binary zip**（如 `apache-jmeter-5.6.3.zip`）
2. **解压到没有中文、没有空格的路径**，例如 `D:\tools\apache-jmeter-5.6.3`
   ⚠️ 路径含中文或空格在 Windows 上容易出各种怪问题
3. 进入 `bin\`，双击 **`jmeter.bat`** 启动 GUI

### 1.3 切中文界面

启动后：`Options → Choose Language → Chinese (Simplified)`

想永久生效：编辑 `bin\jmeter.properties`，把 `language=` 改成：

```properties
language=zh_CN
```

### 1.4 记住这条纪律 ⚠️

> **GUI 只用来"编写和调试"脚本；真正压测必须用命令行 `-n` 模式。**

原因（面试必答）：

- GUI 模式下，每个监听器（查看结果树、聚合报告）都会**实时渲染**，非常消耗 CPU 和内存
- 于是**压测机自己的能力被 GUI 吃掉一大半** → 你压出来的数字里混着"GUI 的开销"
- 而且 GUI 能开的线程数很有限，压不高

## 2. 最重要的一个概念：元件的作用域（Scoping）

**这是 JMeter 面试出现率最高的考点，也是初学者最大的坑。**

规则：**JMeter 的元件是一棵"树"。除了"取样器（HTTP 请求）"以外，其他元件（配置元件、断言、监听器）都作用于"它所在的层级及其子节点"。**

```
测试计划
└── 线程组
    ├── HTTP 请求默认值        ← 作用于整个线程组下的所有请求
    ├── HTTP 信息头管理器      ← 同上（全局头）
    ├── 简单控制器「需鉴权的接口」
    │   ├── HTTP 信息头管理器  ← 只作用于这个控制器里的请求 ✅
    │   ├── HTTP 请求 GET /api/users
    │   └── HTTP 请求 POST /api/orders
    └── HTTP 请求 POST /api/login   ← 不受上面那个头管理器影响
```

**一句话**：**元件放在哪一层，就影响哪一层往下。** 想只影响某个请求 → 挂成它的子节点。

⚠️ **这就是下面第 3.9 步能不能拿到 token 的关键。**

## 3. 手把手建测试计划

被测接口清单（来自你的 `mock_server.py`）：

| 接口 | 方法 | 需要 token | 请求体 |
|---|---|---|---|
| `/api/login` | POST | ❌ | `{"username":"admin","password":"123456"}` |
| `/api/register` | POST | ❌ | `{"name":"...","age":18}` |
| `/api/users` | GET | ✅ | — |
| `/api/users` | POST | ✅ | `{"name":"...","age":18}` |
| `/api/users/{id}` | GET | ✅ | — |
| `/api/orders` | POST | ✅ | `{"user_id":N,"product":"...","amount":10}` |

### 3.1 建线程组

右键「测试计划」→ 添加 → 线程（用户）→ **线程组**

| 字段 | 填写 | 含义 |
|---|---|---|
| 线程数（用户） | `10` | **并发用户数** |
| Ramp-Up 时间（秒） | `5` | 5 秒内把 10 个线程**逐步**拉起 |
| 循环次数 | `10` | 每个线程跑 10 轮 |
| （勾选）调度器 | 先不勾 | 想"压 60 秒"时才用 |

> **为什么 Ramp-Up 不是 0？** 0 代表"瞬间拉起全部线程"，那是**冲击测试**；
> 真实用户是逐渐进来的 → 用 ramp-up 模拟。**面试可能问这个。**

**总请求数 = 10 线程 × 10 循环 = 100 次（每个接口）。**

### 3.2 加 HTTP 请求默认值（抽公共配置）

右键「线程组」→ 添加 → 配置元件 → **HTTP 请求默认值**

| 字段 | 填写 |
|---|---|
| 协议 | `http` |
| 服务器名称或 IP | `127.0.0.1` |
| 端口号 | `8000` |

之后每个 HTTP 请求就**不用再填地址**了，只填路径。

### 3.3 加全局请求头

右键「线程组」→ 添加 → 配置元件 → **HTTP 信息头管理器**

新增一行：

| 名称 | 值 |
|---|---|
| `Content-Type` | `application/json; charset=utf-8` |

> ⚠️ **Authorization 头不要加在这里！** 见 3.9 —— 因为登录之前 token 还不存在，加在这里会发出字面量 `${token}` 导致 401。

### 3.4 建事务控制器「1. 登录」

右键「线程组」→ 添加 → 逻辑控制器 → **事务控制器**，命名为 `1. 登录`

> **事务控制器干什么**：把其下的多个请求合并统计为**一个事务**。
> 于是聚合报告里会出现"`1. 登录`"这一行的 TPS 和响应时间 —— 这才是**业务视角**的指标。
> ⚠️ 勾选 **"生成父样本"（Generate parent sample）** 才会单独统计。

在它下面加：右键 → 添加 → 取样器 → **HTTP 请求**

| 字段 | 填写 |
|---|---|
| 名称 | `登录` |
| 方法 | `POST` |
| 路径 | `/api/login` |
| 消息体数据（Body Data） | `{"username":"admin","password":"123456"}` |

### 3.5 加断言

**① 响应断言**（右键「登录」请求 → 添加 → 断言 → 响应断言）

| 字段 | 填写 |
|---|---|
| 应用范围 | 主样本 |
| 测试字段 | `响应代码` |
| 模式匹配规则 | 等于 |
| 要测试的模式 | `200` |

**② JSON 断言**（右键「登录」请求 → 添加 → 断言 → **JSON 断言**）

| 字段 | 填写 |
|---|---|
| Assert JSON Path exists | `$.code` |
| Expected Value | `0` |

> **为什么要两层断言？** 因为你的接口是"**HTTP 200 + 业务码判成败**"。
> 只断 HTTP 200 会漏掉"业务失败但 HTTP 成功"的情况 —— 这正是你 `core/assertions.py` 里 `assert_status_code` + `assert_code` 两层设计的原因。**面试问"断言怎么做"，就答这个。**

### 3.6 加 JSON 提取器（**关联**）

右键「登录」请求 → 添加 → 后置处理器 → **JSON 提取器**

| 字段 | 填写 |
|---|---|
| 名称 | `提取token` |
| JSON Path expressions | `$.data.token` |
| 匹配数字（0 代表随机） | `1` |
| 变量名称 | `token` |
| **Default Value** | `TOKEN_NOT_FOUND` ← **一定要填！** |

> ⚠️ **默认值必须填**：不填的话，提取失败时变量会保持字面量 `${token}` 传给后续请求，
> 于是你收到一个 401，但根本不知道是"没提取到"还是"接口有问题"。填了默认值，后续请求会发 `Authorization: TOKEN_NOT_FOUND` —— **一眼看出是关联失败**。
>
> 这就是"**让错误看起来像错误**"的思路，和你之前修的 `{"name": 123}` 崩溃、以及"响应≠事实"是同一种工程直觉。

### 3.7 建事务控制器「2. 注册」（含数据唯一化）

右键「线程组」→ 添加 → 事务控制器，命名 `2. 注册`
其下加 HTTP 请求：

| 字段 | 填写 |
|---|---|
| 名称 | `注册` |
| 方法 | `POST` |
| 路径 | `/api/register` |
| 消息体数据 | `{"name":"压测用户_${__threadNum}_${__time(,)}","age":18}` |

**`__time(,)`** 是 JMeter 内置函数，返回**毫秒时间戳**。**`__threadNum`** 是线程编号。

> ⚠️ **为什么两个都要，不能只用 `__time()`？**
> 因为 `__time()` 是**毫秒精度**，10 个并发线程很可能在同一毫秒内各发一个请求 → **撞名** → 服务端返回 1006 → 断言失败。
> 加上 `${__threadNum}`（每个线程唯一）就稳了。
>
> **这就是你前几天在功能测试里踩过的"数据唯一化"问题，在压测里一模一样地又出现了一次。**
> 想更保险也可以用 `${__UUID()}`。

### 3.8 建事务控制器「3. 查询」

右键「线程组」→ 事务控制器，命名 `3. 查询`
其下加 HTTP 请求：`GET /api/users`（或者用 3.7 的 `data.id` 提取后查单条）

如果要查**指定用户**，先在注册请求下加 JSON 提取器：`$.data.id` → 变量 `uid`，
然后请求路径写 `/api/users/${uid}`。

### 3.9 处理需要 token 的请求 ⚠️ 最容易卡住的一步

**把「3. 查询」「4. 下单」放进一个「简单控制器」，然后在那个控制器下挂 HTTP 信息头管理器。**

```
线程组
├── 事务控制器 1.登录        → 提取出 ${token}
├── 事务控制器 2.注册
├── 简单控制器「需鉴权」
│   ├── HTTP 信息头管理器     ← Authorization: ${token}
│   ├── 事务控制器 3.查询
│   └── 事务控制器 4.下单
```

**头管理器内容**：

| 名称 | 值 |
|---|---|
| `Authorization` | `${token}` |

> **为什么不能把 Authorization 挂在线程组顶层？**
> 因为线程组下所有请求都会带上它 —— 而**登录请求在 token 还不存在时发出**，会带上字面量 `${token}`。
> 虽然 `mock_server` 的 `_is_authed()` 只校验前缀、恰好能过，但**真实系统一律 401**。
> **正确做法就是利用"作用域"**：把头管理器挂在需要它的那一层。
>
> **这就是第 2 节讲作用域的实际用途 —— 面试问"作用域有什么用"，答这个例子最清楚。**

### 3.10 加监听器

右键「线程组」→ 添加 → 监听器：

- **查看结果树**（调试用，**压测时必须禁用**）
- **聚合报告**（看指标）

> ⚠️ 调试完记得**禁用或删除「查看结果树」** —— 它会把每个请求的完整请求/响应都存到内存里，压测时**几下就把 JMeter 拖死**。这是新手最常见的翻车点。

## 5. 读报告：哪些指标要看

**聚合报告里的列**：

| 列 | 含义 | 怎么用 |
|---|---|---|
| `# Samples` | 请求总数 | 对账用 |
| `Average` | 平均响应时间 | ⚠️ **别只看这个** |
| `Median` | 中位数（P50） | 一半请求比它快 |
| **`90% Line` / `95% Line` / `99% Line`** | **P90 / P95 / P99** | **这才是结论依据** |
| `Min` / `Max` | 最快 / 最慢 | Max 异常大往往意味着有长尾 |
| `Error %` | 错误率 | 压测的核心红线之一 |
| **`Throughput`** | **TPS（每秒完成事务数）** | 吞吐量 |

**两句能立刻区分水平的话**：

> ① **"我不看 Average，看 P95/P99。"**
> 100 个请求里 99 个 10ms、1 个 5s，平均值只有 60ms —— 但那 1 个用户已经骂娘了。**平均值会掩盖长尾。**
>
> ② **"压测要有明确目标，没目标的压测只是跑个数字。"**
> 比如"50 并发下 P95 < 200ms、错误率 < 0.1%"。没目标就没法判断通过不通过。

**还要会看"拐点"**：逐步加大并发（10 → 50 → 100 → 200），TPS 会先涨、然后**不再涨甚至下降**，同时 P95 陡增 —— 那个位置就是**容量上限**。

## 7. 面试高频问题自测（10 题 · 附答案）

> 每题给「**核心答案 + 为什么 + 本项目实例**」。带 📌 的是本项目**实测过的数据**，能直接当证据用。

### 1. 线程组的"线程数"和"Ramp-Up"分别代表什么？Ramp-Up 设 0 会发生什么？

- **线程数** = 并发用户数（同时模拟多少个用户）
- **Ramp-Up** = 用多少秒把这些线程**逐步**拉起（如 5 秒拉起 100 个 ≈ 每秒 20 个）
- **Ramp-Up = 0** → 瞬间拉起全部线程 = **冲击测试（spike test）**
  - 这**不是错**，但改变了测试性质：真实用户是逐渐进来的，0 模拟的是"瞬间涌入"（秒杀、开抢场景）
  - 📌 **副作用本项目实测过**：瞬时建立大量连接会顶爆服务端 accept 队列 —— 100 并发时出现的 58 个 `Connection refused`，本质就是"连接建立速率超过队列容量"（`request_queue_size = 5`）
- **一句话**：Ramp-Up 决定**加压曲线**，它决定你测的是"稳态容量"还是"瞬时抗压"。

#### 🔍 延伸：Ramp-Up 会影响报告里的 Throughput 吗？

**会影响 —— 但它影响的是"平均值"，不是"系统能力上限"。** 这是**测量口径问题**，不是性能问题。

**原因**：JMeter 聚合报告的 Throughput = `样本总数 / 测试总时长`（从第一个样本到最后一个样本）。而 **Ramp-Up 期间是「欠载期」**：线程还没起齐、负载在爬坡，这段时间**算进分母，却贡献不了多少样本** → 平均值被稀释。

**算一遍就懂了**（100 线程 × 循环 10，单请求 10ms，理想情况）：

| Ramp-Up | 大致总时长 | 总样本 | 报告里的平均 TPS | 稳态峰值 |
|---|---|---|---|---|
| **1s** | ≈ 1 + 10 = 11s | 1000 | ≈ **91** | ≈ 100 |
| **10s** | ≈ 10 + 10 = 20s | 1000 | ≈ **50** | ≈ 100 |
| **60s** | ≈ 60 + 10 = 70s | 1000 | ≈ **14** | ≈ 100 |

**平均 TPS 差了 6 倍以上，而系统能力一个字都没变。**

**怎么才能看到真实的稳态 TPS**：

1. **看 HTML 报告的 `Throughput Over Time` 曲线，取「平顶段」** —— 而不是报告顶部那个总平均
2. **拉长稳态阶段占比**：循环数从 20 提到 200，Ramp-Up 那段在总分母里占比变小 → 平均值逼近稳态值
3. **导出 JTL 后按时间窗口切片**自己算，或直接用阶梯加压（Stepping Thread Group）看各阶梯

**⚠️ 实验设计陷阱（做分级测试时必须注意）**

对比不同并发数（10 / 50 / 100 / 200）时，**Ramp-Up 必须固定**（或严格按比例固定），而且**别用整轮平均 TPS 横向对比** —— 否则你把"Ramp-Up 造成的统计差异"当成了"并发能力差异"。

**另一个方向的副作用**：Ramp-Up **过短**（尤其 0）会带来真实的能力损失 —— 瞬间建连顶爆服务端 accept 队列，部分请求**根本发不出去**（📌 本项目那 58 个 `Connection refused`），这时的 TPS 下降是**真的**，不是统计假象。

> **一句话**：Ramp-Up 长 → 报告平均值被欠载期稀释（假降）；Ramp-Up 极短 → 建连失败丢请求（真降）。**看曲线平顶，别只看那个总平均。**

### 2. 什么叫"关联（Correlation）"？不做关联会发生什么？

- **关联 = 把上一个请求响应里的值提取出来，存成变量，供后续请求引用。**
- 典型对象：**token、用户 id、订单号** —— 服务端动态生成、客户端无法预知的值
- **不做关联的后果**：后续请求要么用硬编码的过期值，要么把 `${token}` **原样发出去** → 鉴权失败（401）
- JMeter 实现：**后置处理器** —— JSON 提取器 / 正则提取器 / XPath 提取器
- 📌 本项目：`POST /api/login` → JSON 提取器取 `$.data.token` → 变量 `token` → 需鉴权的请求由 **HTTP 信息头管理器**注入 `Authorization: ${token}`
- **等价物**：这和我 pytest 框架里 `core/extractor.py` + `VariablePool` 是**同一个模型** —— JMeter 用"后置处理器 + 变量"，我用"提取器 + 变量池"。

### 3. JSON 提取器的"默认值"为什么要填？

- **不填的坑**：提取失败时变量**不会自动清空** —— 它会保持"上一次成功的值"或未替换的字面量。于是后续请求带上 `${token}`（原文）→ 你收到 401，却**根本分不清**是"没提取到"还是"接口真有问题"
- **填了之后**：失败时变量被重置为默认值（如 `TOKEN_NOT_FOUND`）→ 请求头里出现 `Authorization: TOKEN_NOT_FOUND` → **一眼就知道是关联失败**
- **本质**：**让失败看起来像失败**（fail loud）。默认值不是为了"兜底跑通"，而是为了"**失败了能立刻认出来**"
- 📌 同一思路在本项目出现多次：`assertions._body_preview()`（断言失败附响应体）、`assert_required_fields()`、以及"响应必须带 `Content-Length`，否则客户端会一直等"

### 4. 事务控制器有什么用？和"多个请求"有什么区别？

- **作用**：把其下的多个请求**合并统计为一个"事务"**（勾选「生成父样本」后会在报告里单独出现一行）
- **区别**：

  | | 看的是 | 回答什么问题 |
  |---|---|---|
  | 单个 HTTP 请求 | **接口级**指标 | "这个接口多快" |
  | 事务控制器 | **业务级**指标 | "**完成一件业务**要多久"（≈ 多个接口耗时之和） |

- **为什么要**：用户感知的是"下单成功要多久"，不是"某个接口 0.5ms"。**只有业务级指标才能对标 SLO**
- 📌 本项目报告里 8 行 = 4 个**事务**（`1.登录`/`2.注册`/`3.查询`/`4.下单`）+ 4 个**请求**（`登录`/`注册`/`查询`/`下单`）—— **这是正常现象，不是重复统计**
- ⚠️ **注意**：报告的「总计」只统计**叶节点**（真实请求），父事务是聚合视图、**不重复计入**。所以 100 线程 × 20 循环 × 4 请求 = 8000，而 8 行相加会是 16000

### 5. 断言应该断哪些层面？只断 HTTP 200 有什么风险？

- **三层**（本项目三层都有）：
  1. **HTTP 层**：响应码（200 / 400 / 401 / 404）
  2. **业务层**：业务码 + 关键字段（`$.code == 0`）
  3. **数据层**：再查一次接口 / 库，确认"**真的落库了**"
- **只断 HTTP 200 的风险**：**大量系统的业务失败也返回 HTTP 200**，靠响应体里的 `code` 区分成败。此时只断 200 → **把失败当成功**（假通过）
  - 本项目恰好是"HTTP 400 + 业务码 1006"这种规范做法，但**不能假设所有被测系统都这样**
- **数据层为什么必要**：**"响应 ≠ 事实"**。服务端可能"**回了 1006 但照样写入**"（漏 `return`），也可能"更新接口只回显、没落库"。只断响应会漏掉这类缺陷
  - 📌 本项目并发用例的第 ③ 条断言就是为此：`GET /api/users` 过滤同名 → **必须只有 1 条**

### 6. 为什么压测必须用非 GUI 模式？

- **GUI 下每个监听器都会实时渲染**（尤其「查看结果树」，会把每个请求的完整请求/响应报文都存进内存）
- **后果**：压测机自己的 CPU / 内存被吃掉一大块 → **压出来的数字里混着"压测工具的开销"** → 污染被测指标
- 另外 GUI 能开的线程数有限，压不高
- **正确定位**：

  | 模式 | 用途 |
  |---|---|
  | GUI | **编写 + 调试**（看请求头、响应体、错误详情） |
  | 命令行 `-n` | **压测执行** |

- 📌 **本项目的直接实证**：关掉 PyCharm 释放约 3GB 内存后，同一配置（200 线程）的 TPS 从 **1908 涨到 3360** —— 压测机资源对结果的影响是**数量级**的，不是"一点误差"

### 7. 元件的作用域规则是什么？举一个必须用作用域解决的例子。

- **规则**：除**取样器（HTTP 请求）**外，其他元件（**配置元件、断言、后置处理器、监听器**）都作用于「**它所在的层级及其所有子节点**」
- **一句话**：**元件放在哪一层，就影响哪一层往下。** 想只影响某个请求 → 挂成它的子节点
- **必须用作用域解决的例子（本项目实际用法）**：**`Authorization` 头管理器不能挂在线程组顶层**

  ```
  线程组
  ├── 事务控制器 1.登录          ← 此时 token 还不存在
  └── 简单控制器「需鉴权」
      ├── HTTP 信息头管理器       ← Authorization: ${token}   「挂在这一层」
      ├── 事务控制器 3.查询
      └── 事务控制器 4.下单
  ```

  若挂在**线程组顶层**，登录请求会带上字面量 `Authorization: ${token}` —— 本项目 Mock 的 `_is_authed()` 只校验前缀且登录不鉴权，所以侥幸没暴露；**真实系统一律 401**
- 同类例子：「HTTP 请求默认值」挂线程组下 → 该组所有请求共享协议 / 域名 / 端口

### 8. 分布式压测（master/slave）解决什么问题？

- **解决的问题**：**单台压测机的发压能力不够**（CPU / 内存 / 网络带宽 / 本地端口）
- **根本原因**：**压测工具自身也是程序，也消耗资源** —— 压得越高，压测机越可能先到极限
  - JMeter 是**线程模型**：1 个虚拟用户 = 1 个 Java 线程（约 1MB 栈），几千线程就吃掉几 GB
  - 更早到的往往是**网络带宽**：千兆网卡 ≈ 125MB/s，若单响应 10KB，约 **1.2 万 TPS 就撞网卡上限**
- **模型**：`master`（只做两件事：**分发指令 + 汇总结果**，自身**不产生负载**）+ 多台 `slave`（真正产生负载）
- **三个注意事项**：① 每台 slave 都要能访问被测服务；② **各机时间要同步（NTP）**，否则汇总的时间轴错乱；③ master 最好也独立
- **与"压测机分离"的区别（别混）**：

  | 做法 | 解决什么 |
  |---|---|
  | 压测机与被测服务**分离**（两台机） | 二者**互相抢资源**导致的测量污染 |
  | **分布式**（多台压测机） | 单台压测机**发压能力不足** |

  这是两个不同的问题，可以同时需要。

### 9. 聚合报告里你最关注哪几列？为什么平均响应时间不可靠？

- **最关注（按优先级）**：
  1. **Throughput（TPS）** —— 吞吐量，核心结论
  2. **90% / 95% / 99% Line（P90 / P95 / P99）** —— 分位数，体验的真相
  3. **Error %** —— 错误率，红线
  4. 次要：`# Samples`（用来对账：线程数 × 循环 × 请求数）、`Min` / `Max`（**Max 对"停顿"极敏感**）
- **为什么平均值不可靠**：**它会被长尾污染，又会把长尾掩盖掉。**
  - 📌 **本项目实测**：200 线程某轮 `Median 12ms` 而 `Average 109ms`（差 **9 倍**），最慢一个 `Max 2909ms`
    - 只看 **Avg** → "响应时间从 0.75ms 恶化到 109ms，整体崩了"
    - 看 **Median** → "**一半请求仍有 12ms**，是少数极端慢请求把均值拉高了"
    - 看 **P99** → "**1% 的请求超过 1 秒**" ← 这才是要修的问题
- **一句话**：**平均值是一个被极端值绑架的数字。** 结论要基于分位数，`Avg` 只能当粗看。

### 10. 如果 TPS 上不去，你的排查顺序是什么？（**最重要的一题**）

> 核心原则：**先证明不是"测量工具"的问题，再往下查。** 否则后面所有分析都建立在错误前提上。

**第 0 步 · 排除测量问题**（最容易被跳过，也最伤）

| 检查 | 怎么查 |
|---|---|
| 压测机 CPU / 内存 | 任务管理器 |
| 压测机 GC | `-Xlog:gc*`（📌 本项目实测最长停顿仅 19.5ms → **GC 假设被推翻**） |
| **网络带宽** | 任务管理器 → 网络；千兆网卡 ≈ 125MB/s，万级 TPS 就可能撞上限 |
| 本地端口 / TIME_WAIT | `netstat -ano \| findstr TIME_WAIT` |
| GUI 是否开着、监听器是否没关 | 关掉再跑 |
| **压测机与被测服务是否同机** | 📌 本项目 200 线程时内存占用 11.9/15.7GB，**可用不足 4G 触发换页** → 同一配置两次结果差 **2.3 倍** |

**第 1 步 · 用"现象组合"判断瓶颈层次**（📌 本项目三轮都是这么定位的）

| 现象组合 | 瓶颈层次 |
|---|---|
| **错误率升 + 延迟没恶化 + TPS 还在涨** | **连接 / 资源层**（请求根本没进去）→ 📌 58 个 `Connection refused`，根因 `request_queue_size=5` + `protocol_version=HTTP/1.0` |
| TPS 停滞 + P95 陡增 | 服务端**处理能力**到顶 |
| **Median 正常但 Max 大得离谱** | 某处发生**停顿**（GC / 换页 / 网络重传） |
| **TPS 随数据量增长而下降** | 存在 **O(n) 逻辑**或**缺索引** → 📌 注册判重与列表查询都是 O(n)，连跑 5 次 TPS 从 3360 单调降到 1708 |

**第 2 步 · 被测服务内部**
- 线程 / 进程模型（单进程？GIL 限制？）
- 有没有全局锁、**锁的粒度是否过大**（持锁做 I/O）
- 有没有 O(n) 遍历
- 连接池 / 超时配置

**第 3 步 · 下游依赖**
- 数据库：慢查询、连接数、锁等待
- 缓存：命中率
- 第三方接口

**第 4 步 · 网络与系统层**
- 带宽、RTT、丢包
- 文件描述符上限、内核参数

**收尾 · 如实报告边界**

> 如果确实摸不到服务端上限（比如压测机就是瓶颈），**不要写"压不上去"**，而是写：
> **"在 X TPS 下服务端资源使用 < 30%、P99 = Y ms，系统运行健康；本轮受压测机能力限制，未触及服务端容量上限。"**
>
> **明确区分"压测机上限"与"被测服务上限"，是性能测试的基本素养。**

## 附：JTL 文件怎么打开、怎么解读

### 1. Excel 打开中文乱码？—— 是编码问题，**数据没坏**

现象（Excel 里看到）：

```
鏌ヨ               ← 其实是「查询」
鐧诲綍              ← 其实是「登录」
涓嬪崟              ← 其实是「下单」
绾跨▼缁?1-100        ← 其实是「线程组 1-100」
```

**原因**：JTL 是 **UTF-8** 编码；而 **Excel 双击打开 CSV 时不检测 UTF-8**，直接按**系统 ANSI 代码页**（中文 Windows = GBK / 936）去解码 → 变成乱码。

**验证一下就知道数据没坏**（拿「登录」试）：

- `登录` 的 UTF-8 字节：`E7 99 BB E5 BD 95`
- 按 GBK 两两拆：`E799` → `鐧`、`BBE5` → `诲`、`BD95` → `綍`
- 拼起来 = **`鐧诲綍`** ✅ **与 Excel 显示逐字吻合**

> **⇒ 字节没坏，只是被用错了编码去读。** 换个正确的读法，原文就回来了。

📌 这个坑和你项目里 `requirements.txt` 缺 BOM 导致的 `UnicodeDecodeError: 'gbk' codec...` **是同一族** —— 都是「UTF-8 内容被 GBK 解码」。

### 2. 三种解法

| 解法 | 做法 | 评价 |
|---|---|---|
| **A. 用导入向导** | Excel →「数据」→「从文本/CSV」→ 选文件 → **文件原始格式选 `65001 : Unicode (UTF-8)`** → 加载 | ✅ 不用改文件 |
| **B. 给文件加 BOM** | 在头部加 `EF BB BF`，Excel 双击即可识别 UTF-8 | 每次压测会重写 JTL，需跑完补一次 |
| **C. 干脆别用 Excel** | 用 **HTML 报告** 或 **pandas** 读 | ✅✅ **最推荐** |

补 BOM（PowerShell，确实要用 Excel 时）：

```powershell
$c = Get-Content .\r100.jtl -Raw -Encoding UTF8
[IO.File]::WriteAllText(".\r100_utf8bom.jtl", $c, (New-Object Text.UTF8Encoding $true))
```

### 3. 更该做的：JTL 不是给人「看」的

**JTL = 原始样本流水（每行一个请求）**，逐行看没有意义。它真正的用途：

| 用途 | 工具 |
|---|---|
| 看**聚合统计 / 图表** | `jmeter -g r100.jtl -o report` → HTML 报告 |
| **自定义切片分析**（按秒算 TPS、取稳压段、按 label 算 P95） | **pandas**（见下） |

```bat
jmeter -g r100.jtl -o report
```

（要求 JTL 由 `-n` 非 GUI 模式产生）

### 4. 用 pandas 做 JTL 分析（推荐）

```python
import pandas as pd

df = pd.read_csv("r100.jtl", encoding="utf-8")

# ⚠️ 先过滤掉「事务控制器」生成的父样本：
#    父样本 URL 为空/null，是聚合视图、不是真实请求。
#    不过滤 → TPS 会翻倍（4 个请求 + 4 个事务 = 8 行）
real = df[df["URL"].notna() & (df["URL"] != "null")]

# ① 各接口统计（对标聚合报告）
print(real.groupby("label")["elapsed"].agg(
    样本数="count", 平均="mean", 中位="median",
    P95=lambda s: s.quantile(0.95), 最大="max"))

# ② 按秒算 TPS —— 看「稳压段」，而不是整轮平均（呼应 Ramp-Up 那节）
real = real.assign(sec=real["timeStamp"] // 1000)
print(real.groupby("sec").size().head(20))

# ③ 加压曲线：活动线程数怎么涨的（直接验证 Ramp-Up）
print(df.groupby("sec")["allThreads"].max().head(20))
```

### 5. JTL 字段速查（默认列布局）

以两行真实样本为例：

```
1789811584781,1,查询,200,OK,线程组 1-100,text,true,,258,221,1,1,http://127.0.0.1:8000/api/users/5527,1,0,1
1789811584781,1,3.查询,200,"Number of samples in transaction : 1, number of failing samples : 0",线程组 1-100,,true,,258,221,1,1,null,1,0,1
```

| # | 列 | 值 | 含义 |
|---|---|---|---|
| 1 | `timeStamp` | 1789811584781 | 请求开始时间（epoch 毫秒） |
| 2 | **`elapsed`** | 1 | **响应时间（ms）** ← 报告里的 Avg / P95 就是对它的统计 |
| 3 | `label` | 查询 / 3.查询 | 样本名 |
| 4 | `responseCode` | 200 | HTTP 状态码 |
| 5 | `responseMessage` | OK | 状态消息 |
| 6 | `threadName` | 线程组 1-100 | 线程名 |
| 7 | `dataType` | text | 响应类型 |
| 8 | `success` | true | 成功 / 失败 |
| 9 | `failureMessage` | (空) | 失败原因 |
| 10 | `bytes` | 258 | 响应字节数 |
| 11 | `sentBytes` | 221 | 请求字节数 |
| 12 | `grpThreads` | 1 | 本线程组活动线程数 |
| 13 | `allThreads` | 1 | **全部**活动线程数 |
| 14 | `URL` | http://…（父样本为 `null`） | 请求地址 |
| 15 | **`Latency`** | 1 | **延迟**（发出请求 → 收到首字节） |
| 16 | `IdleTime` | 0 | 空闲时间 |
| 17 | **`Connect`** | 1 | **建立 TCP 连接耗时**（复用连接时为 0） |

**从这两行能读出三件事**：

1. **`查询` 与 `3.查询` 是同一件事的两行** —— 前者是**真实 HTTP 请求**（有 URL），后者是**事务控制器生成的父样本**（URL 为 `null`，消息为 `Number of samples in transaction : 1`）。
   ⇒ 这就是「勾选生成父样本」的效果。**做统计时要去重**。
2. **`elapsed = 1`（ms）** 很快 —— 但**单条样本不能代表整体**（要看 P95 / P99）。
3. **`allThreads = 1`** —— 样本发生瞬间只有 1 个活动线程。这几行在**文件开头**，对应 **Ramp-Up 刚开始的第 1 个线程**。
   ⇒ **按秒看 `allThreads` 的变化，就能直接验证上一节的「加压曲线」**（是否从 1 逐渐升到 100）。

> ⚠️ **`Connect` 列是个宝**：它记录**建立 TCP 连接的耗时**。keep-alive 生效、连接被复用时 `Connect = 0`；每个请求都新建连接时则一直非 0。
> **这是验证「HTTP/1.1 连接复用是否真的生效」的原始证据**（呼应第 2 节的 keep-alive 讨论）。
