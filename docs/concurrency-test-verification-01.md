# 01 并发用例检测力验证（变异测试）

> 验证对象：`01-api-test-framework/testcases/test_register.py::test_register_concurrent_same_name`
> 验证日期：2026-09-17
> 验证工具：`01-api-test-framework/tools/mutation_check_register.py`（本次新增）

## 一、要回答的问题

用例注释写着：

> 这是"判重与写入在同一临界区"的证据：若判重退回锁外，这里会稳定出现多个 200（把 bug 复现出来）。

所以要用例具备两个能力：

| 被测代码 | 用例应有的结果 |
|---|---|
| `mock_server.py`（判重在**锁外**，TOCTOU 漏洞版，`:171-174` 判重 / `:176` 进锁） | ❌ 红 |
| `mock_server2.py`（判重在**锁内**，修复版，`:183-199`） | ✅ 绿 |

**实测结果：两种情况都绿。** 用例没有区分力，因此它**不能作为"修复有效"的证据**。

## 二、验证方法：变异测试

"用例通过了"只能证明"当前代码没触发失败"，不能证明"用例有检测能力"。
标准做法是**变异测试（Mutation Testing）**：往被测代码里注入已知缺陷，看用例是否变红。

- 变红 = 缺陷被捕获（killed），用例对该缺陷有效；
- 仍绿 = 缺陷存活（survived），用例对该缺陷是盲的。

本项目的素材天然齐备：`mock_server.py`（判重锁外）与 `mock_server2.py`（判重锁内）正是一对"缺陷/修复"。

脚本构造的变异档位（只改 `_handle_register` 一处，**从不修改 `mock_server.py`**）：

| 档位 | 改什么 |
|---|---|
| `remove` | 整块删掉重名校验（上界对照，必须变红） |
| `base` | 原样不改 = 当前真实代码（下界对照） |
| `1/5/20/50` | 在【判重 → 加锁】之间注入 `time.sleep(d)`，人为放大 TOCTOU 窗口 |

## 三、实测数据

每档独立起一个 Mock 进程（独立端口），用 `BASE_URL` 覆盖把用例打过去。

| 变异档位 | 轮数 | 变红 | 变绿 | 判定 | 断言报出的"实际成功数" |
|---|---|---|---|---|---|
| 移除判重 | 3 | 3 | 0 | 被杀死 ✅ | 8, 8, 8 |
| **基线（判重锁外，真实代码）** | **8** | **0** | **8** | **存活 ❌** | **全部未触发断言** |
| 判重→加锁 注入 1ms | 8 | 8 | 0 | 被杀死 ✅ | 3,2,2,4,4,3,5,5 |
| 注入 5ms | 3 | 3 | 0 | 被杀死 ✅ | 8, 8, 8 |
| 注入 20ms | 3 | 3 | 0 | 被杀死 ✅ | 7, 8, 8 |
| 注入 50ms | 3 | 3 | 0 | 被杀死 ✅ | 8, 8, 8 |

**检测下限 ≈ 1ms**（1ms 起 8/8 检出；真实窗口档 0/8 检出）。

## 三·补、两个靶向变异（"用例自检清单"的落地验证）

常见的并发用例自检清单会写：

| 故意改坏 | 用例应该 | 没红说明 |
|---|---|---|
| 把判重挪回锁外（回到 TOCTOU 版本） | 🔴 变红（出现多个 200） | 你的并发用例没真的并发（没测到竞态） |
| 让服务端"返回 1006 但照样写入" | 🔴 变红（库里多条） | 你只断了响应，没断数据 |

**务必注意：上表第一行的预期在本项目上不成立，必须修正。** 实测（`--modes remove,toctou,write-on-dup --rounds 3`）：

| 靶向变异 | 结果 | 被哪条断言抓住 |
|---|---|---|
| ① 判重挪回锁外（TOCTOU） | **0/3 变红 —— 存活 ❌** | 未触发任何断言（假通过） |
| ② 返回 1006 但照样写入 | **3/3 变红 —— 被杀死 ✅** | **③数据事实（库里 8 条同名）** |
| 上界对照：整块移除判重 | 3/3 变红 —— 被杀死 ✅ | ②响应分布（实际 8 个 200） |

结论：

- **变异②是"确定性缺陷"，与并发时序无关，所以必然被抓到** —— 而且抓它的正是第 3 条断言。
  这里有一个不需要额外实验的逻辑证据：**pytest 在断言②失败时会立刻停止**，
  而实测命中的是③，说明**②当时是通过的** —— 即该变异体的响应分布
  「1×200 + 7×1006」**完全符合期望**，只断响应的用例一定会放过它，
  唯一拦住它的是"再去查一次库"那条断言。
  **这就是"不要只断响应、要断数据事实"最好的活证据。**
- **变异①在当前 Mock 上测不出来**（原因见第四节：μs 级窗口 vs 5ms GIL 时间片）。
  要让这一行真正成立，必须**同时放大窗口**——脚本里的毫秒档本质上就是
  "toctou + 注入延迟"，实测 1ms 起即可稳定杀死。所以正确的自检清单应写成：

  > 把判重挪回锁外**并且用可控耗时放大窗口**，用例应该变红；
  > 若不红，说明并发用例没真的并发。

## 四、根因：三层叠加

### 1. 真实 TOCTOU 窗口是**亚毫秒**的
窗口 = `_handle_register` 里"判重完成"到"进入临界区"之间的几十条字节码。
Mock 的判重是内存字典遍历（`any(u["name"] == name for ...)`），表里只有个位数记录，耗时约微秒级。

### 2. GIL 只在"时间片到期/字节码计数达标"时才切换
CPython 3.12 的切换间隔是 `sys.getswitchinterval()` = **5ms**。
线程要撞进这个概率 = 窗口(≈μs) / 时间片(5ms) ≈ 0.02%，还要 8 个线程同时撞上 —— 概率趋近于 0。
反过来说：**只要判重耗时超过 5ms 时间片，控制权必被让出，竞态就必然发生** —— 这正是 1ms 档能稳定复现、而 base 档 0/8 的原因（`time.sleep` 会主动释放 GIL）。

### 3. 本地 Mock 把并发缺陷"测没了"
真实系统的判重=查数据库 / 查 Redis / 调远程校验，耗时天然是 **1~50ms**，远超 GIL 时间片。
Mock 为了"跑得快"把这段耗时压成 0 → 竞态窗口一起被压没了。

**所以问题不在用例的断言设计，而在被测对象不具备真实系统的时序特性。**
这条用例现在实际验证的是"8 个请求排队时，后来的会被拒"（串行语义），
而不是它声称的"同时到达时也不会重复写入"（并发语义）。

> 报告里的旁证：8 个响应耗时呈 2/2/3/3/4/5/3/2 ms 的递增分布、总耗时 17ms ——
> 说明 8 个请求实际是被错开处理的，根本没有"同时"到达判重点。

## 五、改进方案（按性价比排序）

### 方案 A（推荐）：给 Mock 注入可控的"判重业务耗时"
让 Mock 具备真实系统的时序特性，而不是为了"过测"而改。

在 `mock_server.py` 增加命令行参数（如 `--register-delay-ms`，默认 0 保持向后兼容），
并在 `_handle_register` 的**判重之后、写入之前**插入 `time.sleep(delay)`。

关键：注入位置是**语义位置**（判重与写入之间），因此在两个版本上落点不同——

| 版本 | sleep 落在哪 | 结果 |
|---|---|---|
| `mock_server.py`（判重锁外） | **锁外** | 8 个请求穿透判重 → 用例红 ✅ 证明用例有效 |
| `mock_server2.py`（判重锁内） | **锁内** | 被锁串行化 → 用例绿 ✅ 证明修复有效 |

这样用例才真正获得区分力，且"延迟"本身可解释为"模拟真实判重开销"。

### 方案 B（不推荐）：靠加线程数 / 加重复轮次硬撞
实测 8 线程 8 轮全绿；要撞开 0.02% 概率的窗口，需要成百上千轮，
即使偶然撞红也是**不可复现的 flaky**，比"测不出来"更糟。

### 方案 C：把竞态测试下沉为进程内单元测试
绕开 HTTP，直接构造 handler 实例调用 `_handle_register`，配合 `sys.setswitchinterval()` 强制细粒度切换。
检测力更强，但 `_handle_register` 强依赖 `_send` / `_read_json` 的 I/O，改造成本较高。

## 六、面试话术（可直接背）

> "我写过一条 8 线程同名注册的并发用例，一开始跑是绿的，但我没敢信。
> 我用变异测试验证了一下——在服务端判重和写入之间注入延迟，人为放大竞态窗口。
> 结果很有意思：把判重移到锁外这个 bug，本地 Mock 上 8 轮跑下来一次都没抓出来；
> 但只要把窗口放大到 1ms 以上，用例 8/8 全部报红。
>
> 根因是本地 Mock 的判重是内存字典遍历，窗口只有微秒级，
> 而 CPython 的 GIL 切换间隔是 5ms —— 线程根本来不及在那个窗口里被调度，
> 所以并发缺陷被"测没了"。真实系统判重要查库查缓存，耗时 1~50ms，远超时间片，竞态就会真实发生。
>
> 结论是：Mock 不能只追求"跑得快"，还要还原真实系统的时序特性。
> 我最后给 Mock 加了可控的判重耗时参数，用例才真正获得了区分 bug 版和修复版的能力。"

**这条话术的价值**：同时展示了 L3（看出静默问题）、L5（把"用例有效吗"拆成可验证的变异实验）和 L6（讲清权衡），
且是绝大多数候选人不会主动做的动作。
