# 性能测试（perf）

> **压测对象**：`mock_server.py`（标准库 `ThreadingHTTPServer` + 内存表）
> **工具**：Apache JMeter 5.6.3（**非 GUI 模式**）
> **日期**：2026-09-19 ~ 09-20

---

## ⚠️ 先说清局限（比结论更重要）

**这些数字不代表任何业务容量。** 原因：

- 被测对象是**本地 Mock**：**单进程** + **一把全局锁** + **O(n) 全表遍历判重/查询**；
- **压测机与被测服务在同一台机器上**（同一台机器既跑 JMeter 又跑服务，互相抢资源）；
- 所以这里的数据**只用于验证方法论、定位瓶颈**，不能拿去对标任何真实系统。

> 主动声明局限，是因为**性能测试的第一条纪律是"知道自己在测什么"**。

## 快速开始

### 1. 起被测服务（独立终端，保持开着）

```bat
cd 01-api-test-framework
..\.venv\Scripts\python.exe mock_server.py --port 8000
```

### 2. 跑压测（另开终端，非 GUI 模式）

```bat
cd <jmeter 安装目录>\bin
jmeter -n -t "<本目录绝对路径>\jmeter\login-flow.jmx" -Jthreads=100 -l r100.jtl -e -o rep100
```

| 参数 | 含义 |
|---|---|
| `-n` | **非 GUI 模式** —— 压测必须用；GUI 的监听器会实时渲染，**吃掉压测机资源、污染被测指标** |
| `-t` | 测试计划文件 |
| `-Jthreads=100` | 覆盖线程数（计划里用 `${__P(threads,20)}` 读取） |
| `-l r100.jtl` | 结果数据（CSV，每行一个样本） |
| `-e -o rep100` | 生成 HTML 报告（**目录必须不存在或为空**） |

### 3. 看结果

- `rep100\index.html` → **Statistics** 表（含 P90/P95/P99）、**Errors** 表
- 终端 summary 一眼看关键值：

```
summary = 8000 in 00:00:05 = 1654/s Avg: 0.75 Min: 0 Max: 64 Err: 0 (0.00%)
          ↑样本数         ↑TPS    ↑平均   ↑最快 ↑最慢  ↑错误数
```

**核对样本数的公式**：`线程数 × 循环次数 × 每迭代请求数`
（如 100 × 20 × 4 = 8000；对不上说明有没注意到的因素，比如父样本、被禁用的元件）

## 测试计划说明

### 业务流（4 个事务）

```
事务「1.登录」 POST /api/login            → JSON 提取器取 data.token → 变量 token
事务「2.注册」 POST /api/register         → JSON 提取器取 data.id    → 变量 uid
事务「3.查询」 GET  /api/users/${uid}
事务「4.下单」 POST /api/orders  {"user_id": ${uid}, ...}
```

### 几个关键设计点

| 设计 | 原因 |
|---|---|
| 线程数用 `${__P(threads,20)}` | 可用 `-Jthreads=N` 从命令行梯度加压，无需每次开 GUI 改配置 |
| 注册名用 `压测用户_${__UUID()}` | **压测数据必须唯一化** —— 并发下毫秒时间戳会撞名（撞唯一键 → 1006） |
| 下单 body 里 `user_id` **不加引号** | JMeter 提取出的变量**永远是字符串**；数字字段加引号会变成 `"403"`，与 int 键不匹配 |
| JSON 提取器设置**默认值** | 提取失败时变量保持字面量/上次值 —— 设默认值能让失败"看起来像失败" |
| 断言两层：响应断言(200) + JSON 断言(`$.code==0`) | 本服务是"HTTP 200 + 业务码判成败"，只断 HTTP 码会漏掉业务失败 |
| Authorization 头管理器**挂在需鉴权的控制器下** | 利用**元件作用域**：登录前 token 不存在，全局挂载会发出字面量 `${token}` |

## 实测结论

### 第一轮：连接层瓶颈（100 并发）

**现象**：1.30% 错误率，但 **TPS 大幅上涨、响应时间没有恶化**。

| 错误类型 | 数量 |
|---|---|
| `Connection refused` | **58** |
| `401 Unauthorized` | 28 |
| `400 Bad Request` | 18 |

**推断**：*"错误率上升 + 延迟没恶化 + 吞吐还在涨" ⇒ 请求根本没进去，问题在连接层。*

**根因**：Python 标准库两个默认值

| 默认值 | 问题 | 修复 |
|---|---|---|
| `TCPServer.request_queue_size = 5` | accept 队列只有 5，瞬时连接超出即被 RST | 子类化 → `128` |
| `BaseHTTPRequestHandler.protocol_version = "HTTP/1.0"` | 每个请求都新建 TCP 连接，反复冲击那个小队列 | `"HTTP/1.1"`（响应有 `Content-Length` 才能开） |

**验证**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `Connection refused` | 58 | **0** |
| Avg | 1.27ms | **0.38ms** |
| P95 | 3.00ms | **1.00ms** |

**响应时间降到 1/3** —— keep-alive（连接复用）的收益。

### 第二轮：因果链分析（1 个根因 + 2 类级联）

修复连接层后只剩 **87 个 400**，分布极规律：**注册/查询/下单各 29，登录 0**。

```
根因：注册撞名失败（1006）→ uid 提取不到
  ├─ 查询：GET /api/users/    → 路径末尾为空 → 400
  └─ 下单：{"user_id":, ...}  → 非法 JSON → 400
```

**登录 0 错**，因为它的 body 写死、不依赖任何提取变量 —— 这个对比本身就指向"问题在变量上"。

**修复**：注册名改用 `${__UUID()}` → **87 个错误一起归零**。

> **方法论**：*看错误不能看有几类，要看有几条因果链。* 修掉根因，衍生现象会一起消失（本次实证：修连接层 → 401 自己没了）。

### 第三轮：数据量导致的系统性退化（单变量对照实验）

**设计**：200 线程，**连跑 5 次不重启服务**（唯一变化的自变量 = 表内数据量，每轮 +4000 条）。

| 次数 | TPS | Avg | P99 | Max |
|---|---|---|---|---|
| 1 | **3360.64** | 1.88ms | 13.99 | 77 |
| 2 | 3163.93 | 10.28ms | 39.00 | 102 |
| 3 | 2546.96 | 25.44ms | 104.00 | 266 |
| 4 | 2072.00 | 44.09ms | 190.99 | 534 |
| 5 | **1707.76** | **65.52ms** | 286.98 | 572 |
| **6（重启后）** | **3346.58** | **1.85ms** | **14.00** | **77** |

**TPS 降 49%、Avg 涨 35 倍，且单调；清空数据后立刻恢复到起点（差 0.4%）。**

⇒ **数据量是唯一根因，因果闭环。**

**机制**：两条 O(n) 路径

| 路径 | 代价 |
|---|---|
| 注册判重 `any(u["name"] == name for u in self.users.values())` | 每次遍历全表 |
| 列表查询 `list(...)` + `json.dumps` 整张表 | 每次序列化全表；并发下 CPU 打满 |

**证据**：5 次里**注册始终是最慢的接口**（表空时也是：2.11ms vs 下单 1.68ms）→ 判重开销恒存在，随表增长被放大。

> **⭐ 最有价值的一课**：同一实验在被污染的环境下（内存仅剩 3.8GB）做过一次，**结论完全相反** —— TPS 序列无单调性，一度误判"数据量不是主因"。
> **噪声不会让你"看不准"，它会让你"看反"。** 所以**排除环境噪声不是优化项，而是前提**。

---

## 可复用的方法论（6 条）

1. **看错误不看"几类"，看"几条因果链"** —— 一个根因会生出多种表象。
2. **"错误率升 + 延迟没恶化 + 吞吐还在涨" ⇒ 问题在连接/资源层，不是处理能力。**
3. **"Median 正常但 Max 大得离谱" ⇒ 某环节发生了停顿**（GC / 换页 / 网络重传），而不是"负载高"。
4. **同一配置跑多轮、记录实验条件**（线程数、循环数、是否重启、内存占用）；波动 > 30% 时先解决可复现性，**再谈性能**。
5. **不只看平均值，看 P95/P99** —— 实测中位数 12ms 而平均 109ms（差 9 倍），平均值被长尾污染。
6. **明确压测对象与测量边界** —— 压测机与被测服务不分离时，测出来的是"这台电脑"的极限。

## 附：`gil_demo.py`（GIL 演示）

```bat
..\.venv\Scripts\python.exe perf/gil_demo.py --cpu-only   :: 不需要服务
..\.venv\Scripts\python.exe perf/gil_demo.py              :: I/O 实验需要 Mock 服务在跑
```

对比「串行 / 多线程 / 多进程」在两种任务下的表现，实测结果：

| 场景 | 4 线程 | 4 进程 | 赢家 |
|---|---|---|---|
| **CPU 密集型**（纯计算，全程持有 GIL） | 1.01x | **2.04x** | **多进程** |
| **I/O 密集型**（HTTP 请求，等待时释放 GIL） | **3.99x** | 3.66x | **多线程** |

**结论**：CPU 密集型用多进程；I/O 密集型用多线程（效果不差且开销更小）。

> 注意：多进程实验里被并发执行的函数**必须是顶层函数**（需 pickle 到子进程），且 Windows 上必须有
> `if __name__ == "__main__":` 保护，否则子进程会无限重启。
